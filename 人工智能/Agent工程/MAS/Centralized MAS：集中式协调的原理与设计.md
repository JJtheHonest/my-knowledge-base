# Centralized MAS：集中式协调的原理与设计

## 1. 定义与研究视角

Centralized MAS 的关键是存在负责全局协调的角色：理解整体目标、组织任务、分配工作、跟踪进展并决定如何继续。下文称该角色为 LeadAgent（LA），工作 agents 为 SubAgents（SA）。LA 的职责是一种逻辑角色，不必一定由一个 LLM、一个进程或一台机器独占。

研究重点是 coordination：谁决定下一步、依据什么信息、谁与谁交换什么、怎样处理依赖、如何形成最终产物。不把“多次模型调用”或“多个 agent 同时运行”本身视为充分的协调机制。

本笔记以架构原理与参考设计为主，区分架构的定义性特征与可选择的实现机制。架构名称不是统一的协议标准；为便于与 Hybrid 比较，下文用“纯集中式”指主要经 LA 调度和转发协作信息的形式。

## 2. 协调职责与两种任务组织

LA 可以承担：

- **规划**：识别目标、约束、依赖与验收标准。
- **分配**：把任务交给具有适当工具、上下文或专长的 SA。
- **上下文管理**：把相关证据与约束发给需要的 SA。
- **进度管理**：收集产物、判断阻塞、调整计划与预算。
- **整合与结束决策**：验证任务覆盖情况，汇总或选择最终答案。

SA 在局部目标内执行推理、调用工具、产生产物，并报告证据、限制和未解决问题。

集中式组织既可以是**互补分工**，也可以是**冗余求解**：

| 组织方式 | SA 在做什么 | 整体完成条件应关注什么 |
|---|---|---|
| 互补分工 | 分别处理必要的不同子任务 | 必要产物齐备，接口和全局约束满足 |
| 冗余求解 | 分别解决整个任务或验证同一候选 | 已获得可接受的完整解，满足预设选择/验证规则 |

不能把适用于冗余求解的“任一有效解即可停止”直接套到互补分工。

## 3. 参考执行流程

以下是可采用的设计，不是所有系统必须遵循的固定步骤：

```text
接收目标、资源预算与验收条件
    → LA 建立初始计划与任务依赖
    → 指定各 SA 的目标、输入、交付格式和边界
    → 调度当前可执行的工作
    → 收集 SA 的结果、证据、状态与阻塞原因
    → 检查整体目标
        ├─ 有缺口：补充上下文、重新分配或修改计划
        ├─ 预算耗尽：返回有明确限制的阶段性结果
        └─ 已满足：验证并汇总/选择最终产物
    → 输出答案及其依据
```

只有可并行且依赖已满足的工作才适合同时执行。集中式不等于并行式，也可以按依赖顺序调度，或者在事件到达时继续执行，不一定使用同步 round。

### 一轮与一次迭代不是同一层级

- iteration：一个 SA 内部的一次推理、工具调用或局部行动。
- work round：SA 在一次指导下完成的一段工作，可能包含多次 iteration。
- coordination round：系统收集一批工作结果并调整安排的一个阶段。

这些术语需要由具体实验定义；不能仅凭同名 `max_rounds` 比较不同系统的预算。

## 4. 产物与状态设计

建议 SA 交付的不只是自由文本 findings，还包括可追踪的工作产物。例如：

```text
任务与产物版本
主要结论或文件/数据表
证据与来源
已完成的检查
未解决问题与依赖
状态：仍在执行 / 候选已就绪 / 阻塞 / 已交付
```

这些字段是参考设计，不是标准协议。目的在于让 LA 能判断“拿到了什么、能否使用、还缺什么”。

必须区分：

1. **执行结束**：函数或任务不再运行。
2. **子任务交付**：SA 提供了可用产物。
3. **整体完成**：所有必要目标与约束已满足。
4. **结果正确**：通过任务相关的验证或评估。

提交动作通常是生命周期事件，不天然提供正确性证据。最终已有完整且可验证的答案时，LA 可以直接选择输出，不必为了形式再次调用 LLM 改写；需要整合多个互补产物时，才应明确安排 synthesis。

## 5. 优势、代价与适用条件

以下是设计分析与待验证假设，不是对任何系统的性能保证。

可能的优势：全局目标与依赖较容易统一管理；便于追踪责任、分配预算和处理阻塞；对明确可拆解且需要整合的任务，协调路径直观。

可能的代价：LA 可能成为决策与上下文瓶颈；经 LA 转述的证据可能被压缩或误解；规划错误可能影响多个 SA；每轮协调也消耗模型调用与等待时间。

在一个 LA 与 N 个 SA 的星形通信示意中，逻辑链路规模随 N 线性增长；但这不等于实际 token、延迟或协调难度也线性增长。消息长度、上下文重复、轮次与依赖结构都要计入。

更适合优先尝试的条件：子任务边界和交付要求可表达、需要统一决策、不同能力或工具之间有可识别依赖。不应预设它总优于单 agent 或其他 MAS。

## 6. 示例：有证据约束的财务问题求解

示意设计：LA 要求回答某公司的某项指标并给出依据。

- SA-A 检索报表，交付相关数据、来源、日期与计量单位。
- SA-B 在输入就绪后计算，交付公式、结果和可重算过程。
- SA-C 检查期间、单位和口径是否一致。
- LA 根据计算与检查结果生成完整回答；缺少必要数据时退回补充，而不是把任何一个 SA 的结束当作整体完成。

这个例子体现依赖调度和产物验收，不意味着每个问题都值得拆成三个 agents。

## 7. 研究与评估问题

- 分工是否减少了遗漏，还是只把单 agent 的工作切碎并增加交接？
- LA 的指导是否真正改变了 SA 的行动，而非重复原任务？
- 失败来自规划、局部执行、信息转发，还是最终整合？
- 在实际 token、工具调用、延迟和失败重试成本接近时，协调是否仍有收益？
- 停止决策是否依据已收集且可用的产物，而不只是布尔状态？

## Observations

- [insight] 集中式的核心是全局协调权，不是所有 SA 必须并行或完全隔离。
- [insight] 任务分工方式决定完成条件：局部交付不能自动等同于全局完成。
- [decision] 以协调职责、信息流、交付约束与验证机制理解架构，区分架构原则与实现选择。
- [idea] 用结构化产物和任务依赖替代仅靠自由文本汇报的完成判断。
- [question] 在什么依赖结构下，集中协调的收益超过交接与决策成本？
