# Hybrid MAS：全局协调与局部协作的结合

## 1. 定义与研究视角

本笔记用 Hybrid MAS 指一种工作定义：保留 LA 的全局规划和整合职责，同时允许工作 agents 通过直接消息、共享产物或其他机制开展局部协作，不必把每一项交互都先交给 LA 转述。

它结合两种协调通路：

- **纵向协调**：LA ↔ SA，管理全局目标、任务分配、依赖与预算。
- **横向协作**：SA ↔ peers，交换相关证据、核对接口、交叉检查并局部修订。

“Hybrid”不是一种统一的固定算法。不同文献可能用它描述不同的混合维度，因此阅读时必须具体说明混合了什么、谁保留哪些决策权。

为便于与纯 Centralized 比较，本笔记强调新增的局部协作通路；不声称所有有 peer 消息的系统必然被文献归入同一类别。

## 2. 为什么结合两种通路

设计动机是：全局协调与局部信息交换解决不同问题。

- LA 适合维护跨任务目标与依赖、分配全局资源、处理局部无法解决的冲突。
- peers 可以直接讨论具体数据、假设和接口，减少所有细节经 LA 转述的需要。

这只是设计动机，不意味着混合后必然同时获得两者全部优点。它也会引入重复通信、过期信息与权限边界等协调成本，需要通过实验验证。

## 3. 一种连贯的参考流程

```text
LA 明确目标、预算与验收条件
    → 分配子任务，定义 SA 交付接口
    → SA 独立或并行形成阶段性产物
    → 根据依赖、分歧或证据缺口，安排相关 peers 交流
    → SA 验证与修订各自产物
    → 将最新版本、证据与未解决问题汇报给 LA
    → LA 检查整体覆盖、解决跨团队冲突
        ├─ 仍有缺口：调整分工或再次安排局部协作
        └─ 已满足：整合或选择最终产物并提交
```

这是参考设计，不是唯一正确顺序。最重要的约束是：若交流用于改善最终答案，其产生的新证据和修订必须能够影响后续决策或输出。

已有完整且验证通过的产物，可以直接选择输出；有互补结果时才需要明确的整合步骤。不能把“必须最后再调用一次 LA”当成 Hybrid 的定义。

## 4. 交流可以放在哪里

| 设计 | 何时交流 | 主要研究问题 |
|---|---|---|
| 汇总前评审 | 阶段性候选形成后，最终输出前 | 一轮交叉检查是否足够发现重要问题 |
| 轮内交流 | 每个协调轮中交换必要信息 | 提前协同的收益能否覆盖持续通信成本 |
| 事件触发交流 | 出现冲突、阻塞、接口变化或证据缺口时 | 触发器是否可靠，是否会漏掉必要沟通 |
| 局部团队协作 | 把强依赖任务组织为临时子团队 | 局部自主与全局一致性如何兼顾 |

以上是可选择或组合的设计方式，不代表都已在某个项目或框架实现。Hybrid 不应被简化为“Centralized 结束后机械增加一轮”。

## 5. 谁应与谁交流

建议按任务关系决定，而不是默认所有 SA 阅读全部 peers 的所有历史。

例如：数据提供者与计算者核对数据口径；实现者与测试者核对接口和失败证据；存在相互矛盾结论的 agents 交换来源。LA 可决定交流对象，也可以允许 SA 在边界内主动请求协助。

这引出几个必须明确的问题：

1. 谁可以发起 peer 请求，谁可以拒绝或转交？
2. 什么信息可以共享，哪些数据、工具与权限不能转移？
3. peers 可以自行修改局部方案，还是只能提出建议？
4. 哪些冲突必须上报 LA，哪些可以局部解决？
5. 何时认为局部讨论结束，其产物如何并入全局状态？

直接发送一段文本是信息通路，不自动构成完整的请求—回应—验收协议。自由聊天也不应被当成协调能力的充分证据。

## 6. 共享产物与版本一致性

一个可采用的设计是给每个产物附带：任务标识、作者、版本、依赖版本、来源、检查结果与未解决问题。

其目的不是堆砌字段，而是解决：

- SA-A 修订数据后，SA-B 是否需要重新计算？
- LA 收到的是交流前版本，还是交流后版本？
- 两个 agents 同时修改同一产物时，谁决定接受哪一版？
- 最终答案引用的证据是否已经过期？

共享存储只是载体；还需要更新、通知与冲突规则，才能形成可靠协调。

## 7. 生命周期与全局完成条件

阶段性候选、局部交付、整体完成与外部正确性应分别判断。

如果 SA 需要吸收 peer 信息，就应保留修订能力；若已经执行不可逆提交，可在提交前安排评审，或让独立角色评估产物，不应假设任何环境都能恢复。

全局结束条件应同时关心：必要任务是否完成、关键分歧是否有处理结果、最新产物是否已收集、输出是否符合约束。预算耗尽也可以结束运行，但应明确标为资源限制下的结果，不能悄悄称为成功。

## 8. 优势、风险与适用条件

以下是设计分析与研究假设，不是性能排名。

可能优势：保留全局目标控制，同时让局部专业问题直接交流；有机会减少 LA 的细节转述负担；能同时组织互补分工与交叉验证。

主要风险：纵向与横向消息重复；局部修订与全局计划冲突；不同角色使用不同版本；交流过多挤占执行预算；LA 与 peers 的责任不清导致重复劳动或无人负责。

更值得尝试的条件：任务既有明显全局依赖，又存在需要专业交互的局部问题。若任务很简单，额外通路可能只有成本；若局部可以完全独立，也未必需要持续横向交流。

## 9. 示例：数据、计算与审查的协作

示意设计：LA 安排数据 agent、计算 agent 与审查 agent。

1. 数据 agent 提供报表数据及来源。
2. 计算 agent 发现分子分母期间不一致，直接向数据 agent 请求核对。
3. 审查 agent 检查公式、单位和题目口径，反馈给相关 peers。
4. peers 修订并记录变更；不能解决的题意歧义交给 LA。
5. LA 根据最新产物形成最终答案，或说明仍存在的歧义。

这里 LA 不必转发每次单位核对，但仍负责整个回答的目标与一致性。

## 10. 如何评估 Hybrid 的真实增益

- 相比纯集中式，peer 通路传递了什么新增且有用的信息？
- 局部交流是否改变了工具使用、证据检查或最终答案？
- LA 的协调负担是否下降，还是只增加了一套重复沟通？
- 在接近的实际 token、模型调用、工具调用与时间预算下，收益是否保留？
- 是否需要消融不同的交流时机、对象和信息粒度？
- 评分输入是否确实反映交流后的最新产物？

## 11. 代表资料与阅读边界

## Observations

- [insight] Hybrid 的关键是全局协调与局部协作如何分工，而不是额外增加一轮对话。
- [insight] 信息交流必须进入产物更新与决策，才构成有意义的协调过程。
- [decision] 将交流安排在仍可修订的阶段，保证最新产物与最终输出一致。
- [idea] 以冲突、依赖和证据缺口触发局部交流，并明确上报 LA 的条件。
- [question] 哪些通信边和交流时机最有价值，哪些只是重复开销？
