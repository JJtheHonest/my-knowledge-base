# Decentralized MAS：同伴协作、辩论与结果聚合

## 1. 定义与概念边界

本笔记关注没有单一 LA 持续掌握全局内容决策权的同伴协作。agents 根据局部状态、peer 信息和共同协议作出行动，协调来自信息交换与规则，而非完全依赖一个 lead 的分配与批准。

去中心化不等于没有调度程序，也不等于必须把计算部署到多台机器；内容决策权、通信拓扑、运行基础设施与最终聚合器是否集中，是不同维度。研究时应明确声称在哪个维度去中心化。

**Multi-agent debate 是其中一种重要模式，但不是 Decentralized MAS 的完整定义。** 去中心化 agents 也可以交换证据、协商分工或共同更新产物，不必人人回答同一道完整问题。

下面重点讨论“独立候选 → 同伴检查 → 修订 → 聚合”的 debate 模式。本文提供参考设计，不规定所有实现必须照此执行。

## 2. Debate 协调的基本思路

先保留多个相对独立的初始判断，再允许 peers 看到彼此的理由与证据，对分歧作出回应。

```text
共同任务与讨论规则
    → 各 agent 独立形成候选答案和依据
    → 交换相关候选、证据与不确定性
    → 检查分歧、指出问题、补充验证
    → 各自修订，或有理由地坚持原答案
    → 达到预算或预定停止条件
    → 按明确规则选取、验证或整合最新结果
```

Du 等的 multiagent debate 工作采用多个模型实例先提出答案与推理，再经多轮讨论形成最终答案，是这一思路的代表资料［1］。其报告的任务收益不能自动推广到所有模型、任务和讨论协议。

初始多样性可以来自不同提示策略、信息来源、模型、工具或检索结果。给 agents 起不同角色名称并不保证它们获得互补信息或产生独立错误，这是需要通过实验检查的假设。

## 3. 需要设计的协调机制

### 3.1 谁看到谁的信息

可采用全连接、邻居交流或选择性路由。若 N 个 agents 每轮各向其他所有 agents 发送一次消息，则有 N(N−1) 次有向传递；这只是该全连接模式的计数，不是所有去中心化系统的复杂度。

应明确传递的是最终结论、证据、推理摘要、完整历史，还是特定问题。更多文本不自动意味着更多有效信息。

### 3.2 怎样保持可比较的轮次

同步设计让 agents 基于上一轮的统一快照更新，便于解释实验；异步设计可在新信息到达时更新，但需要版本、去重和过期信息规则。两者都是设计选择，不能把同步 debate 当作唯一实现。

### 3.3 候选就绪不等于退出讨论

建议区分：

- **本轮候选就绪**：已有一份可供 peers 阅读的版本，仍可修订。
- **最终交付**：按协议不再修改，或已发生不可逆的环境操作。

若一有答案就永久退出，早期完成者无法吸收 peer 信息。对于会产生真实副作用的任务，应在不可逆动作前完成讨论，而不是随意恢复已终结的任务。

## 4. 讨论、投票、共识和正确性是四件事

- **讨论**：交换信息，检查分歧与理由。
- **投票**：按某种选票规则表达支持。
- **共识**：在规定的相等性判断、参与者和支持阈值下达到一致条件。
- **正确性**：结果符合任务要求或外部事实，需要独立验证依据。

它们不必同时存在。讨论后仍可保留分歧；投出最高票也不一定达到严格多数或共识阈值；达成一致更不意味着答案正确。

### 常见聚合选择

| 方法 | 核心操作 | 需要特别说明 |
|---|---|---|
| 归一化后频次选择 | 按任务定义合并等价答案，再计数 | 数值、单位、日期与允许误差怎么处理 |
| 显式评审投票 | 评审者阅读候选和证据后投票 | 选票依据、平票、弃权与偏差控制 |
| 验证后选择 | 用计算、测试或来源检查候选 | 验证覆盖了什么，哪些仍不确定 |
| 证据整合 | 将互补部分合为最终产物 | 如何处理矛盾与追踪来源 |

不能把这些方法都笼统称为“多数投票”。尤其长文本不同不代表结论不同，文字相似也不代表事实条件相同。

## 5. 停止条件与未达共识的处理

参考条件可包括：达到讨论预算；候选在预定窗口内稳定；关键分歧已验证；达到事先定义的支持门槛。稳定或高支持率只是停止信号，不是正确性证明。

应预先规定未达共识时的动作，例如保留多个候选与分歧、补充外部验证、交给评审器，或按明确回退规则选取。不要在事后把任意赢家都命名为“共识答案”。

## 6. 优势、风险与适用条件

以下是设计分析，不是对性能的保证。

可能的优势：保留多个视角，使理由与证据相互暴露；减少所有推理都依赖单一 LA 规划的情况；适合研究错误发现和相互修订过程。

主要风险与研究假设：相关性错误可能让多人一起犯错；缺乏证据的说服、盲目趋同或复制可能制造表面共识；通信与讨论也可能挤占实际求解预算。

更值得尝试的条件：任务存在可比较的候选结论，参与者具有一定互补证据或推理路径，且争议可通过证据或工具检验。若任务主要是明确的串行依赖流程，自由 debate 未必是首选。

## 7. 示例：比较同一财务指标的不同候选

示意流程：agents 先独立检索、计算某个指标，再交换候选结果和报表来源。一位 agent 使用期末值，另一位使用平均值；讨论应识别口径差异并检查题意，而不是直接多数表决选数字。

最终先按期间、单位和公式验证，再对可比较的结论聚合。若题意确实模糊，应说明不同条件下的答案，而不是为了全体一致掩盖分歧。

## 8. 评估怎样才算有效协调

- 相比首轮独立候选，讨论后新增了什么证据或修正？
- 哪条 peer 消息导致哪次修订？修订是改对还是改错？
- 最终支持率与外部正确率如何关联？
- 同样实际预算下，收益来自交流，还是来自更多独立求解与工具调用？
- 参与者是否真的参与多轮，而不是仅在日志里重复旧答案？

## Observations

- [insight] 去中心化是协调权与交互规则的问题，不等于没有运行时或必须物理分布式部署。
- [insight] Debate 的价值应体现在证据、验证或修订的增益，而不只是对话轮数。
- [decision] 区分候选就绪与最终交付，区分频次选择、评审投票、共识与正确性。
- [idea] 记录 peer 消息到答案修订的因果链，比较有效纠错与盲目趋同。
- [question] 在哪些任务和信息差异下，讨论优于相同预算的独立求解加验证？
