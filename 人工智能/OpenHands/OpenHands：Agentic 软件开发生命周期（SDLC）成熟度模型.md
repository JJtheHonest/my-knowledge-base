### 1. 总体范式

Agentic SDLC 的基本范式是：由生命周期事件触发 Agent，Agent 获取相关上下文，执行一段边界明确的工作，产出可追踪的工程对象，再通过测试、基线、规则或人工审查决定下一步。

```text
生命周期事件 → 上下文收集 → Agent 执行 → 工程产物 → 自动验证 → 人工决策或后续触发
```

每个能力点都可以用同一组问题描述：触发条件是什么、Agent 能访问什么、它要完成什么、结果写回哪里、成功和失败如何判断。

### 2. 需求与问题进入

#### （1）错误报告分类

**做法原则**：新错误进入系统后，Agent 自动完成分类、贴标签、相似问题去重和负责人路由，分类结果直接写回问题管理系统。

**注意细节**：分类依据应包括错误类型、影响范围、严重程度、所属组件和重复关系。去重需要保留关联问题，避免合并后丢失不同版本、环境或用户的证据。低置信度结果应进入人工确认队列。

**流程示例**：

```text
新错误报告 → 提取标题、日志、环境和组件 → 相似问题检索 → 生成标签与严重度 → 关联重复问题 → 路由给团队或负责人
```

#### （2）工作量估算

**做法原则**：工单进入待处理列表时，Agent 根据历史相似任务、实际耗时和任务复杂度生成估算，并在任务完成后用实际结果校准估算依据。

**注意细节**：相似任务不能只按标题匹配，还应考虑修改范围、依赖数量、测试要求和风险。估算应保留依据、置信度和假设，避免把 Agent 的单点判断当成确定承诺。

**流程示例**：

```text
工单进入待处理列表 → 提取任务特征 → 检索历史相似工单 → 对比估算与实际耗时 → 生成工作量和置信度 → 任务完成后回写实际结果
```

#### （3）客户反馈转化为计划工作

**做法原则**：Agent 按计划从支持渠道收集客户反馈，将重复反馈聚合，把可执行反馈转化为待办事项，并维护反馈与待办事项之间的关联。

**注意细节**：要区分功能请求、缺陷、使用障碍、咨询和无效反馈。转化时应保留原始反馈、用户影响和出现频率；涉及隐私的信息需要脱敏；无法形成工程任务的反馈应归档并说明原因。

**流程示例**：

```text
定时读取支持渠道 → 提取反馈主题和用户影响 → 聚合同类反馈 → 判断反馈类型 → 创建或更新待办事项 → 回链原始反馈
```

### 3. 代码库理解与设计

#### （4）代码库映射

**做法原则**：Agent 持续维护代码库的模块、入口、依赖、数据流和测试边界；代码合并后更新架构文档和模块图，为后续设计与实现提供当前上下文。

**注意细节**：映射必须标注生成时间、对应提交和不确定部分。自动生成的架构信息需要通过代码、构建配置和测试交叉验证，不能把过期文档当成事实。大仓库应支持按服务、模块或调用链局部查询。

**流程示例**：

```text
代码合并 → 扫描目录、依赖、入口和测试 → 更新模块关系 → 生成架构文档与图 → 标记变化和不确定关系 → 供设计与开发任务检索
```

#### （5）设计文档和 RFC 审查

**做法原则**：新的设计文档或 RFC 打开、更新或进入评审状态时，Agent 自动按照结构化检查项审查，并把反馈发布到原文档或评审线程。

**注意细节**：审查应区分事实错误、遗漏风险和设计偏好；每条反馈都要指向具体段落并说明影响。检查范围应覆盖需求、边界、接口、数据迁移、兼容性、失败处理、测试、观测和运维。Agent 不能替代架构负责人对取舍的最终判断。

**流程示例**：

```text
RFC 创建或更新 → 读取需求和相关代码 → 按检查项审查 → 生成带位置和严重度的反馈 → 发布到评审线程 → 作者修订后再次触发
```

### 4. 问题到实现

#### （6）错误重现

**做法原则**：新错误进入修复流程后，Agent 优先尝试在隔离环境中重现，并把重现命令、环境、输入、输出和测试结果附加到工单。

**注意细节**：重现环境要尽量固定版本、依赖、配置和数据。成功重现应保存最小复现步骤或回归测试；失败也必须记录尝试过的条件和缺失信息，明确标记“无法重现”，不能用推测代替证据。

**流程示例**：

```text
新错误 → 收集堆栈、版本、请求和环境 → 构造最小复现 → 运行测试或启动服务 → 保存输出与失败证据 → 附加复现结果或无法重现说明
```

#### （7）工单转 PR

**做法原则**：工单达到明确的“就绪”状态后触发 Agent；Agent 阅读任务和代码，完成实现、测试和验证，并打开带有任务关联的 PR 草稿。

**注意细节**：就绪条件应明确范围、验收标准、测试命令和权限边界。Agent 生成的 PR 应包含变更摘要、测试结果、未解决问题和风险。修改范围、依赖升级、数据库变更和安全相关操作应设置额外检查点。

**流程示例**：

```text
工单满足就绪条件 → Agent 获取任务和代码上下文 → 修改代码 → 添加或更新测试 → 运行验证 → 创建关联 PR 草稿 → 回写工单状态
```

#### （8）从聊天或问题评论委派任务

**做法原则**：在 Slack 线程或 GitHub 问题评论中明确提及 Agent，即可使用该讨论上下文启动开发任务，并将进展和结果回写原线程。

**注意细节**：触发语法、仓库、分支、权限和允许的操作范围应清晰。Agent 需要区分讨论中的背景信息和实际指令；任务完成、阻塞、失败和需要人工决策时，都应在原线程留下状态和证据，避免只在 Agent 私有会话中记录。

**流程示例**：

```text
聊天或评论中提及 Agent → 解析任务、仓库和验收条件 → 创建隔离工作环境 → 执行开发与测试 → 在原线程报告进展和结果 → 链接 PR 或阻塞原因
```

### 5. 审查与质量验证

#### （9）自动代码审查

**做法原则**：PR 创建或更新时自动触发 Agent 审查，并在人类审查前发布带有代码位置、问题说明和严重度的内联评论。

**注意细节**：评论应优先关注可验证的问题，例如逻辑错误、边界条件、异常处理、并发、权限、兼容性和测试缺口。要减少重复评论，区分阻断问题与建议项，并在新提交修复后自动关闭或更新已解决评论。

**流程示例**：

```text
PR 创建或更新 → 读取 diff、相关代码和测试 → 执行静态检查与针对性分析 → 生成定位明确的评论 → 根据新提交重新审查 → 输出审查结论
```

#### （10）测试缺口与覆盖率增长

**做法原则**：Agent 按计划扫描高风险且测试不足的代码，围绕实际行为和回归风险生成补测 PR。

**注意细节**：覆盖率数字只是筛选信号，不能作为唯一目标。应结合代码变化、历史缺陷、关键路径和边界条件选择测试对象。新增测试需要验证行为，避免只覆盖执行路径而没有断言业务结果。

**流程示例**：

```text
定期扫描覆盖率、变更和缺陷数据 → 识别高风险测试缺口 → 设计行为测试和边界测试 → 提交测试 PR → 运行测试 → 更新覆盖率与风险记录
```

#### （11）PR 功能 QA

**做法原则**：每个 PR 在隔离环境启动应用，按照验收标准执行关键用户流程，并发布通过或失败的 QA 报告。

**注意细节**：QA 环境、测试数据和启动方式应可重复。报告要记录版本、命令、步骤、实际结果和失败截图或日志。功能验证应覆盖变更影响的真实入口，不能只根据单元测试通过就判定功能正确。

**流程示例**：

```text
PR 构建 → 创建测试环境 → 启动应用 → 执行验收流程 → 检查用户可见行为和状态变化 → 保存证据 → 发布 QA 通过或失败报告
```

### 6. 发布与运行反馈

#### （12）负载性能测试

**做法原则**：按计划或在发布前运行负载测试，将当前结果与稳定基线比较，并自动标记显著性能回归。

**注意细节**：基线要固定测试场景、数据规模、流量模型和环境。至少记录延迟分位数、吞吐量、错误率和资源消耗。异常需要关联版本、配置和依赖变化，避免把测试环境噪声误判为产品回归。

**流程示例**：

```text
计划时间或发布前 → 准备固定负载和环境 → 运行性能测试 → 与历史基线比较 → 分析回归指标和可能变更 → 标记工单或阻断发布
```

#### （13）部署监控

**做法原则**：每次部署后，Agent 持续比较新版本与部署前基线的健康指标，在达到预设阈值时告警，并按既定策略触发人工确认或回滚。

**注意细节**：回滚条件、观察窗口、告警阈值和回滚权限必须预先定义。需要区分短暂波动与持续回归，保留部署版本、指标变化和决策证据。自动回滚前应确保数据库迁移和外部接口变更具备可逆性。

**流程示例**：

```text
部署完成 → 记录版本和基线 → 观察错误率、延迟、流量和资源 → 比较新旧版本 → 正常则结束观察 → 异常则告警、暂停扩容或按策略回滚
```

#### （14）发布说明与变更日志

**做法原则**：版本被标记或发布时，Agent 汇总提交、PR、工单和标签，生成面向使用者的发布说明并发布到指定位置。

**注意细节**：需要过滤内部实现噪声，区分功能、修复、破坏性变更、迁移步骤和已知问题。发布说明应链接相关 PR 或工单，并由负责人确认事实、影响范围和版本号。

**流程示例**：

```text
版本标记 → 收集该版本关联的 PR、工单和提交 → 按用户影响分类 → 生成发布说明 → 校验版本和破坏性变更 → 发布并回链版本
```

#### （15）文档同步

**做法原则**：合并变更后，Agent 判断代码变化是否影响用户或维护者文档；如果影响，则打开文档更新 PR，或按计划直接刷新允许自动维护的文档。

**注意细节**：重点检测 API、配置、CLI 参数、安装部署、用户流程和架构边界变化。文档更新应以当前代码和测试为依据，保留版本范围；不确定的内容应创建待确认项，而不是生成未经验证的说明。

**流程示例**：

```text
代码合并 → 分析变更对用户和维护者的影响 → 定位受影响文档 → 根据代码与测试生成修改 → 打开文档 PR → 由负责人审查并合并
```

### 7. 生产观测与自动反馈

#### （16）生产日志监控

**做法原则**：Agent 持续或按时间窗口分析生产日志，聚合值得注意的错误模式，并为新问题创建带证据的工单。

**注意细节**：日志分析要保留时间范围、服务、版本、环境、样本数量和代表性日志。输入应先脱敏并限制权限。应区分已知噪声、重复事件和新模式，避免同一问题持续创建重复工单。

**流程示例**：

```text
读取时间窗口内日志 → 脱敏并聚合错误模式 → 与已知问题和历史基线比较 → 判断新模式或回归 → 生成摘要和证据 → 创建或更新工单
```

#### （17）指标与行为异常检测

**做法原则**：Agent 按计划扫描业务和系统指标，与历史基线比较，在发现异常时生成包含影响范围、可能关联和下一步调查建议的工单。

**注意细节**：基线应考虑季节性、周期性和业务事件。异常判断要区分单点尖峰、持续偏移和多指标共同变化，并关联部署、配置和外部事件。工单中应明确指标、起始时间、偏离程度和置信度。

**流程示例**：

```text
定时读取指标 → 计算相对基线的偏离 → 检查周期性和相关指标 → 关联部署与配置事件 → 生成影响分析 → 创建带分析结果的工单
```

#### （18）生产错误诊断与修复 PR

**做法原则**：错误追踪事件触发 Agent；Agent 收集错误上下文、定位代码路径、尝试重现、编写修复和回归测试，验证后打开修复 PR。

**注意细节**：生产数据和凭据必须隔离并最小化授权。诊断结论要有堆栈、日志、版本、复现或测试证据。修复 PR 应关联原错误事件，说明影响范围和验证结果；合并、发布和回滚仍应遵循明确的人工审批和自动门禁。

**流程示例**：

```text
错误追踪事件 → 收集堆栈、版本、请求和日志 → 定位代码路径 → 在隔离环境重现 → 编写修复与回归测试 → 运行验证 → 打开修复 PR → 发布后继续观察
```

### 8. 工作流设计的共同约束

无论是哪一个能力点，都应明确以下边界：

- **触发器**：什么事件启动工作，是否允许重复触发。
- **上下文**：Agent 能读取哪些仓库、工单、文档和运行数据。
- **工具权限**：Agent 能否写代码、创建 PR、修改工单或执行部署动作。
- **验收条件**：测试、阈值、基线或人工检查如何定义成功。
- **产物位置**：结果写回哪个系统，如何与原始事件关联。
- **失败处理**：失败时记录什么，是否重试，何时转人工。
- **审查门槛**：哪些操作可以自动完成，哪些操作必须人工批准。

成熟的 Agent 工作流不是让 Agent 无限自主，而是把自主执行放在明确的触发器、权限、证据和审查边界内。

## Observations

- [insight] Agentic SDLC 的基本单元是“事件 → 上下文 → Agent 执行 → 工程产物 → 验证 → 后续决策”。
- [insight] 18个能力点覆盖需求进入、问题处理、设计、实现、审查、测试、发布、运维和生产反馈，构成一个持续反馈的开发闭环。
- [insight] 每个工作流都需要同时定义触发器、上下文、工具权限、验收条件、产物位置、失败处理和审查门槛。
- [insight] Agent 的自主性应建立在可追踪的输入、明确的权限边界和可验证的工程证据上。
- [fact] OpenHands 的核心作用是进入代码库执行开发工作；工单、代码托管、CI/CD、监控和事件编排属于完整 SDLC 系统的协作部分。
- [decision] 设计 Agent 工作流时，将合并、发布、回滚以及生产数据访问等高影响动作设置为明确的门禁或人工决策点。
